**Reviewer#3, Concern # 3:** How does the proposed framework physically ingest 60,000 novel flows per second without triggering hardware rate limits or saturating the OpenFlow control channel?

**Author response:** This is the question we were least able to answer from the submitted evidence, and answering it properly changed what the paper claims.

The 60,606 flows per second reported in the submitted manuscript was an offline feature-extraction and inference rate. It was measured by reading feature vectors from a matrix and scoring them in a loop, with no control channel present, no OpenFlow messages, and no rule installation. It is not an ingest rate and it should not have been presented as one.

We therefore built a control plane and measured the controller rather than the model. The detector runs inside a controller process that exchanges genuine OpenFlow 1.3 messages with switch agents over TCP, with every encoding validated against the os-ken reference parser. The rate we report is defined before it is quoted, because two session configurations produce it and an earlier draft of this reply quoted both as though they were one number. A switch agent is synchronous, so the achieved rate is the number of packet-in exchanges it completed divided by the wall time of the session, including classification and rule installation. The fixed-load session offers 3,000 events per second for 150 seconds with a second agent carrying benign background traffic through the same controller; each sweep session offers one rate for 45 seconds with no background agent and a freshly started controller.

Under the fixed-load session the controller absorbs 114 events per second with detection enabled, at 98.3 percent of one core and 176 MB resident, with a decision taking 6.61 ms at the median and 32.70 ms at the 99th percentile. Enabling attribution for every alert halves that to 61 events per second and nearly doubles the median decision to 11.33 ms.

The sweep sessions bound goodput rather than locating a knee, and we say so rather than presenting the first row as an operating point. Their highest achieved rate is 77 events per second at the lowest rate offered, 500, and that row already returns only 15.5 percent of what is offered, so the controller is saturated at every point of the sweep and the knee lies below 500 where we did not measure. From 1,000 offered upward goodput sits at 34 to 36 events per second and stays there while the median round-trip time nearly triples, so offering more work returns less.

We report the two together rather than reconciling them into one figure.
